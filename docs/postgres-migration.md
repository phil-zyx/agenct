# PostgreSQL migration decision and acceptance plan

Status: design only, assessed against `bb26ace`. PostgreSQL is **not implemented or verified**. SQLite remains the supported database for the single-process private demo. This document does not enable a new deployment mode.

## Decision

Do not replace `rusqlite` with an untested connection-string switch. The application relies on SQLite locking and a process-wide mutex, not just SQLite SQL syntax. A PostgreSQL implementation must preserve authorization, revision checks, publication uncertainty, and worker fencing under independent connections.

Keep the private demo on SQLite until a real PostgreSQL test service is available. The assessment environment has no `postgres`, `psql`, or Docker executable on PATH. No external database was provisioned or contacted. These are verification gaps, not evidence that PostgreSQL cannot be used.

## Exact boundaries to change

- `hub/src/lib.rs`: `Arc<Mutex<Connection>>`, SQLite file lock, inline schema creation, `PRAGMA table_info`, `INSERT OR IGNORE`, `last_insert_rowid`, all task/proposal transactions and row decoders.
- `hub/src/profiles.rs`: connection-specific profile reads and revision-checked writes.
- `hub/src/worker.rs`: connection-specific queue functions, SQLite `IMMEDIATE` transactions, active-job uniqueness, task authorization/revision checks and lease completion.
- `hub/src/publication.rs`: durable intent journal, candidate/task authorization join and transition transactions.
- `hub/src/worker_consumer.rs`: callers currently accept SQLite connections and must use the same repository transaction contracts as queue/publication code.
- Configuration, startup, migrations, integration fixtures, operational backup/restore instructions, and CI must all identify the actual backend. Do not silently fall back to SQLite if PostgreSQL is unavailable.

Extract domain-level storage operations (for example confirm-proposal, claim-job and authorize-publication), rather than exposing a generic connection trait. The transaction boundary belongs inside each operation. An async PostgreSQL pool should not be hidden behind the existing synchronous mutex. Preserve the SQLite implementation and run shared behavioral contracts against both backends.

## SQL and data mapping

Use versioned, checksummed migrations applied under a database migration lock. Preserve every unique constraint, including `(requester, request_id)`, `(owner, request_id)` and the partial unique active-worker index. Use parameter binding and explicit column lists.

- SQLite implicit integer row IDs become PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`; inserts use `RETURNING id`. Import IDs explicitly and reset sequence positions after import.
- Revisions and epoch lease timestamps remain bounded nonnegative signed 64-bit values; reject overflow rather than casting the profile API's `u64` unchecked.
- Owner and UUID-like identifiers remain text initially to avoid changing API identity semantics.
- Keep serialized profile, candidate and publication payloads as text initially. Converting to JSONB is a separate migration and must not silently change digest or exact-content comparisons.
- Event timestamp encoding and ordering must preserve API compatibility. Test conversion explicitly if using `TIMESTAMPTZ` instead of existing timestamp text.
- Replace `INSERT OR IGNORE` with a targeted `ON CONFLICT` clause. Do not suppress unrelated constraint failures.

## Concurrency requirements

A naive SQL port is unsafe even if all single-connection tests pass:

1. **Chat serialization:** per-user Tokio gates only protect one Hub. Retain an explicit single-instance deployment restriction for the first PostgreSQL version. Before replicas, add database-backed per-owner turn leases and fencing, without holding a database transaction during model calls. Late responses from expired owners must not publish results. Model calls must not be automatically replayed on uncertain outcomes.
2. **Startup recovery:** current startup marks every pending message interrupted. A second process would corrupt live turns. Replace this with expired turn ownership recovery before permitting multiple instances.
3. **Worker claim:** replace global SQLite write exclusion with row locking and a conditional atomic claim, typically `FOR UPDATE SKIP LOCKED` plus `UPDATE ... RETURNING`. Lock/revalidate the associated task consistently so task revision changes cannot race authorization. Define one lock order across task, job and publication operations and test it.
4. **Revision updates:** compare expected revision and ownership in the write itself; exactly one racing writer succeeds. Return conflict, not a successful stale write.
5. **Idempotency:** concurrent identical request IDs return one result; changed payloads return conflict. The uniqueness constraint is authoritative, not a prior SELECT alone. Retry serialization failures only within bounded, side-effect-free transactions.
6. **Fencing and publication:** expired worker tokens cannot complete a reclaimed job. Persist `attempting` before any external action and preserve `uncertain` after ambiguous transport failure. Never retry external publication as part of a database transaction retry.

## Offline import and cutover

Use a maintenance window; do not build dual writes for this demo.

1. Stop Hub and consumers, ensure no active external publication, and take a consistent SQLite backup using its backup API. Preserve database permissions and encrypt/store backups according to the operator's policy.
2. Validate the source schema and data. Report orphaned/invalid rows without silently dropping or repairing user data. Preserve IDs, owners, revisions, ordering, proposals, queue status and publication uncertainty.
3. Import all tables into an empty migrated PostgreSQL database inside a transaction. Verify counts and canonical field comparisons, plus identity sequence next values. Keep the source unchanged.
4. Run authenticated read/isolation checks and representative safe writes. Restart and verify persistence. Open traffic only after acceptance succeeds.
5. Before PostgreSQL receives writes, rollback is a configuration reversal to the unchanged SQLite backup. After new writes, rollback requires an explicitly tested reverse migration or restore/reconciliation plan; switching to the old SQLite file would lose data.

## Required evidence before claiming support

A real supported PostgreSQL server must run the backend contract and API suites in CI. Mock SQL, generated SQL, compilation and SQLite tests are insufficient.

- Empty bootstrap, repeated startup, version upgrade, migration failure rollback and simultaneous migration starters.
- Existing Hub API/profile tests parameterized by backend, including private history, bearer identity isolation, proposal approval, revision conflicts and task transitions.
- Separate pooled connections/processes racing proposal confirmation, first profile writes, job enqueue/claim/renewal/completion and publication authorization. Assert unique winners and stable idempotent replay.
- Lease expiry, process crash, stale completion, cancellation/task revision races, deadlocks/serialization failures, and database disconnect during commit. An uncertain commit must be reconciled by operation ID rather than blindly repeated.
- Publication reconciliation without duplicate external effects, with real database commits and a controlled fake external transport.
- SQLite fixture import containing all tables, maximum supported values, Unicode, pending/interrupted messages and uncertain publications; compare records and verify new inserts do not collide.
- Backup restore on a clean server and measured connection limits, timeout behavior and query indexes under a documented workload.

## Smallest implementation sequence

1. Extract and verify storage contracts without changing current SQLite behavior.
2. Add PostgreSQL migrations, pool/configuration and a real CI database fixture.
3. Implement all domain storage operations and run parity plus race tests.
4. Build and test the offline import/verification command and recovery runbook.
5. Release as single-instance PostgreSQL support only. Distributed chat ownership and multi-instance deployment remain a separate, explicitly gated milestone.

This database work does not unblock the disabled code executor, authenticate real OIDC users, configure model credentials, provide hosted access, or verify DSH/GitLab live integrations. Those require their own acceptance evidence.
